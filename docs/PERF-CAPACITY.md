# 长上下文掉速：实测、机制与操作规则（2026-10-31 定稿）

本文件替换 pre-r1 的旧理论（「分配布局轮盘 / 前置偏移决定快慢」）。旧理论的现象数据仍有效，
解释是错的。下面是**本版测到的台阶、能站住的机制、以及明确尚未定论的部分**。

## 0. 一句话结论

16 GB 的 RX 9070 XT 在 Windows 下，驱动只愿意把约 **12.6 ~ 13.6 GiB** 的引擎工作集留在显存，
**而且这个预算当天会漂移约 1 GiB**（桌面占用、驱动内部状态都影响它）。
引擎的提交足迹一旦越线，**整个 KV 池**的物理落点就从显存滑到系统内存，此后每个 step 的 KV 读取走
PCIe 4.0 ×16（实测 ~30 GB/s，驻留时 570-624 GB/s）。**代价与每个 step 真正读多少 KV 成正比**，所以：

- 短提示（2.8K）即使 `--ctx 81920` 也只掉 22%（每 step 只读 ~50 MB KV）；
- 长提示（48K）越线就腰斩（每 step 要读 ~870 MB KV）；
- 126K 提示在 `--ctx 126464`（13.59 GiB）→ 22.9 t/s，`--ctx 131072`（13.67 GiB）→ 10.1 t/s。

⇒ **唯一稳定的操作规则：`--ctx` = prompt + max_new，一个 token 都别多开。**

## 1. 实测台阶（固定 48K 提示，只改 `--ctx`，两次不同时刻各扫一遍）

语料 `tasks_cp64km.txt`（prompt=48,378），KV=`rk4v4-e8`，graph on，其余参数全同：

| 49152 | 0.82 GiB | 12.16 GiB | 30.0 | — | 507 |
| 57344 | 0.96 GiB | 12.30 GiB | 30.0 | — | 500 |
| 65536 | 1.09 GiB | 12.58 GiB | **30.1** | 30.1 | 505 |
| 69632 | 1.16 GiB | 12.64 GiB | **16.8** ← 越线 | — | 433 |
| 73728 | 1.23 GiB | 12.71 GiB | 16.2 | — | 424 |
| 77824 | 1.30 GiB | 12.78 GiB | 17.1 | — | 425 |
| 81920 | 1.37 GiB | 12.85 GiB | 16.7 | 16.7 | 424 |

两个时刻的悬崖位置不同：上午在 **12.58→12.64 GiB**（13.50→13.58 GB），
下午在 **13.53→13.67 GiB**（14.53→14.68 GB）。**同一条命令可以差 1.8×，这不是玄学，是预算漂移。**

形态是**台阶**而不是斜坡：越线后 45%-50% 一跌到底，之后多花容量不再额外惩罚。

真实长文的决定性案例（126,329 token，`tasks_true128kL.txt`）：

| `--ctx` | 引擎总提交 | prefill | decode |
|---|---|---|---|
| 131072 | 13.67 GiB | 222.2 | **10.12** |
| 126464 | **13.59 GiB** | **293.97** | **22.91**（复测 22.93 / 23.01） |

⇒ 2.26× 只来自把 `--ctx` 收紧 4,743 个 token。这也解释了 pre-r1 为什么「126K 有时 23.5 有时 10」。

## 2. 短提示为什么不掉（同一批 `--ctx`，语料 `tasks_t3k.txt`，prompt=2,809）

| `--ctx` | decode |
|---|---|
| 8192 | 36.26 |
| 49152 | 35.9 |
| 65536 | 28.15 |
| 69632 | 27.95 |
| 81920 | 28.34 |
| 98304 | 28.55 |
| 131072 | 28.18 |

⇒ `--ctx` 从 8K 涨到 64K 有 **-22% 的固定容量税**（与提示长度无关），之后**不再随 `--ctx` 继续恶化**，
也没有 48K 提示那种腰斩。**证实掉速与「每 step 读多少 KV」成正比**，而不是「池子大就慢」。

## 3. 机制（含反证与未定论部分）

站得住的三个观测：

1. **权重 arena 恒定 577 GB/s**（`[alloc-bw]` 各档 `--ctx` 一致）⇒ 卡、时钟、驱动都健康。
   慢态下 64 MB D2D 实测 565-852 GB/s（比快态还高）。
2. **启动时对 KV 池做 3 遍全量扫描，恒定只有 ~26-31 GB/s，且各档 `--ctx` 完全相同**。
   这条**不能**用来判断 decode 时的驻留状态——扫描发生在分配时刻，页还没被写过，
   WDDM 尚未把它提升到本地段。**别再拿这一行当放逐证据**（pre-r1/pre-r2 初稿曾这么用，已更正）。
   顺带否证「先读一遍就能提升到显存」：`NINFER_ALLOC_BW=1` 读三遍后 decode 仍 10.13。
3. **`NINFER_DUMMY_MB=1024`（额外提交 1 GiB、永不读写）在 ctx49152 下 decode 不变**
   ⇒ 被放逐的优先目标是「未被触碰的分配」，而不是 KV 池。这也解释了旧数据
   （`NINFER_PREALLOC_MB` 263 MB 会变慢、0/64/129 MB 不变）：受害者的选择取决于谁先被写过。

尚未定论：**谁在什么时候决定落点**。目前只有间接证据（台阶位置与总提交量吻合、短提示不掉、
dummy 当替罪羊、预算随时间漂移）。若后续要收口，做法是在 generation 之后对 KV 池再做一次 3 遍扫描
（需要把 `probe_arena_bw` 暴露到公开头文件 + Engine 暴露池指针），预期快态 570 GB/s、慢态 30 GB/s。

## 4. 为什么只有 ~13.6 GiB 可用（回答「是驱动还是 Windows」）

- 物理显存：17,095,983,104 B = 15.92 GiB。
- WDDM 固定预留：约 1/8 = 2.14 GB（桌面合成、系统进程共用，应用不可用）。
- 桌面/其它进程实测占用：0.78 GB（315+98+82+80+77+67+63 MB）。
- Δ 适配器侧实测：`dedicated(专用)=12,847~12,916 MB`、`shared(共享)=12,778 MB`；
  引擎进程 `Local Usage=12,412 MB`、`NonLocal=0`、`Total Committed=23,587 MB`。
  注意 `Shared Usage` 与 `Local Usage` 数值完全相同 —— **WDDM 对同一批页记两次账**，不是真的双份。
- ⇒ 理论预算 ≈ 14.18 GB，实测台阶 12.6~13.6 GiB（13.5~14.6 GB），差额来自驱动自身不可驱逐分配 +
  命令缓冲/页表 + 当天桌面状态。
- 这是 **Windows WDDM 的行为，不是 AMD 独有 bug**：同一张卡在 Linux/ROCm 下没有 1/8 预留，
  可用接近 15.3 GB。llama.cpp 在这台机器上同样受这个预算约束。

**关键补充（纠正一个常见误解）：`cudaMalloc` 是虚拟超额提交，不等于物理驻留。**
用 alloc-until-fail 探针（`NINFER_VRAM_CEILING`，128 MB 分块）实测：

| 时机 | 可分配到的总量 | 结论 |
|---|---|---|
| 干净进程（未建引擎） | **≥24.00 GiB**（探针上限，仍成功） | 16 GB 卡可以「分配」24 GB ⇒ 分配永不失败 |
| ctx65536 建好引擎后 | 8.25 GiB（再分配仍成功） | 分配侧从来不是瓶颈 |
| ctx131072 建好引擎后 | 7.12 GiB（再分配仍成功） | 同上 |

⇒ 决定快慢的**不是分配成功与否，而是驱动愿意把多少页留在显存**。**「16 GB 只能用 14 GB」的正确说法是：
能分配的远超 16 GB，但能被高速驻留的只有约 13.6 GiB。**

引擎在关键档位的提交量（`[mem]` 行实测）：

| 配置 | weights | seq(KV+状态) | ws | graph | 合计 |
|---|---|---|---|---|---|
| ctx65536 | 11,755,300,864 | 1,494,802,176 | 240,477,440 | 12,582,912 | **13,503,163,392（12.58 GiB）** |
| ctx98304 | 11,755,300,864 | 2,082,006,784 | 240,477,440 | 12,582,912 | 14,091,234,560（13.12 GiB） |
| ctx126464 | 11,755,300,864 | 2,586,635,776 | 240,477,440 | 12,582,912 | **14,592,523,008（13.59 GiB）** |
| ctx131072 | 11,755,300,864 | 2,669,206,272 | 240,477,440 | 12,582,912 | 14,677,134,592（13.67 GiB） |
| ctx126464 + MTP | **12,103,717,888** | **3,061,766,656** | 240,477,440 | **85,983,232** | **15,165,484,352（14.12 GiB）** |
| ctx98304 + MTP | 12,103,717,888 | 2,525,596,672 | 240,477,440 | 85,983,232 | 14,629,291,008（13.62 GiB） |

⇒ **MTP 的固定开销是 +0.57 GB**（mtp 权重 348 MB + draft state 190 MB + verify 图 73 MB）。
所以今天：96K + MTP 提交 13.62 GiB（勉强在内）→ 34.0 t/s 净赚；
126K + MTP 提交 14.12 GiB（越线）→ 10.6 t/s，比 AR 的 22.9 还慢一倍。

## 6. 候选修法（按性价比排序，均未验证）

1. **KV 分块提交 + 显式 offload**（用户 m03323 方向）：只提交窗口内的页，远处 KV 明确放 host，
   并在需要时按块预取。这是唯一能同时做到「256K 装下」和「不按 PCIe 随机读」的路线，工作量最大。
2. **降低每 token KV 字节**：int4 已到 17,920 B/token（K+V 各 4 bit + 双 scale），
   再压只能动 GDN 状态份额或做 3-bit KV。
3. **MTP 瘦身 0.5 GB**（让 126K 也能带 MTP）：verify graph 73 MB 可尝试复用到 AR 图；
   draft state 190 MB 可按 draft window 而非 capacity 分配。这是本版最接近可做的一条。
4. **Linux/ROCm 双轨**：预算 +1.8 GB，126K + MTP 无需放逐。移植成本低（同一棵源码树），但不是本版目标。
5. **砍足迹让 128K 落回预算内**：权重 11.755 GiB、seq 固定状态 320 MB、ws 240 MB、graph 13 MB，
   可腾总量不足 1.2 GiB ⇒ 单靠瘦身做不到 131072 全速，但「ctx 贴紧」已经拿到 126K 的 22.9。

## 7. 给用户的即时结论

- **不要设「固定的安全 ctx」**：预算是 12.6~13.6 GiB 且在漂移，安全值随时刻变化。
  正确做法是 **`--ctx` = prompt + max_new**；若观察到腰斩，先把 `--ctx` 减 4~8K 再看。
- 贴紧后（本版实测）：48K → 30.0 · 96K → 25.2 · **126K → 22.9 t/s**（都由同一套参数取得）。
- **MTP 的可用上限由预算决定**：≤96K 净赚（96K +35%），126K 因多 0.57 GB 越线而必须关闭。
