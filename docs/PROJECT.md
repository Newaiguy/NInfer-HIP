# 项目全貌（0.1.3r2）

一份可以直接拿去做视频脚本的项目说明：**做了什么、为什么这么做、跑多快、边界在哪。**

---

## 1. 一句话定位

在 **一张 16 GB 的 AMD 消费级显卡（RX 9070 XT，RDNA4）** 上，用纯 HIP/C++ 自研引擎跑 **27B 参数的 Qwen3.8**，
支持 **262K 上下文**、**105 tok/s 的投机解码**、**看懂图片**、并且对外提供 **OpenAI 兼容 API** —— 全部在 **Windows** 上。

对比基线：llama.cpp + kvmem（同一台机器、同一块卡、同一批 prompt）。

---

## 2. 为什么不是"又一个 llama.cpp 包装"

| 维度 | llama.cpp | 本项目 |
|---|---|---|
| 平台 | 跨平台（CUDA/HIP/Metal…） | 针对 **RDNA4 / gfx1201 / Windows ROCm** 专门优化 |
| 长上下文 | 通用 KV 卸载 | **三级 KV 记忆**：sink + 常驻窗口 + 主机归档 + query 打分召回 |
| 投机解码 | 通用 draft 模型 | **MTP 头** + 深度自适应（≤64K 用 5，>64K 用 4） |
| 部署形态 | CLI/server | CLI + **OpenAI 兼容服务** + 一键启动器 |
| 中文生态 | 通用 | 针对中文长文档、思考型模型调过默认值 |

现实收益（实测）：

- **prefill 快 1.4–1.6×**（540 vs 332 tok/s @196K）
- 8K 短对话 **decode 105.5 tok/s**（MTP）
- 长上下文准确率与上游**打平**（8 例 needle 问答 8/8 对 8/8）
- 显存只要 16 GB：262K 上下文靠"常驻 32K + 归档到内存"实现

## 3. 三个核心机制

### 3.1 KV 记忆：把 262K 塞进 16 GB

问题：27B 模型 + 262K 上下文的 KV cache 需要 20 GB+，16 GB 卡装不下。

做法（三层）：

```
[ sink 2048 token 永久固定 ] [ 常驻窗口 32768 token ] [ 主机归档池 4096 MiB ]
                                     ↑ 滑窗，被挤出的页 D2H 到内存
```

读长文档时：

1. prefill 阶段逐段滑窗，被挤出的 KV 页**异步归档到主机内存**（不丢）
2. prompt 读完，用这段 prompt 的 query 对归档页打分（**pre-RoPE K 页均值 · pre-RoPE query 均值**）
3. 选出得分最高的**一段 112 页（7168 token）**换回显存，放在"下次滑窗本来就要丢的槽位"——**容量代价为零**
4. 重放最后 chunk，让模型带着召回内容继续生成

两个工程细节值得讲：

- **自适应双段召回**：当第二个峰值"离得够远且分数够高"（gap ≥ 28 页、score ≥ 0.35×top）时，把 112 页预算拆成 50/50 两段，覆盖两份文档；单文档时保持整段。实测：单针任务行为不变，双文档问次峰问题从"答错成另一份文档"变成"答对"。
- **打分为什么不用 RoPE 后的 K**：归档页的 K 已按真实绝对位置旋转过，没法与未来的 query 比较，所以取 RMSNorm 之后、RoPE 之前的 K 做摘要。

实测：

| 上下文 | prefill | decode | 是否命中 |
|---|---|---|---|
| 196K | 540.4 | 29.77 | ✅ |
| 250K | 534.9 | 30.50 | ✅ |
| 261K | 534.1 | 29.79 | ✅ |

> 262,144 是模型位置编码硬顶，不是软件限制。

### 3.2 MTP 投机解码：8K 场景 3× 提速

模型自带 MTP（Multi-Token Prediction）头，可以一次猜多个 token 再批量验证。

- 实测最优草稿深度：**5–6**（8K 场景），而很多实现默认 2 —— 默认 2 等于浪费 32%
- 深度不是越深越好：d2 79.5 / d5 **105.3** / d8 79.8 / d12 75.3 tok/s
- 长上下文时收益衰减：8K 3.0×、32K 1.46×、96K 比 d2 只多 12%
- 所以做成**上下文自适应**：≤64K 用 5，>64K 用 4，`--draft-tokens 0` 即自动

### 3.3 视觉：从"能读图"到"能读位置"

视觉链路：图片 → 切 patch（2×2 merge）→ 视觉塔 27 层 → merger → 196 个 token 拼进文本序列。

这一版把视觉从"大面积内容能认、单色块位置全错"修到 **9/9 全对**，靠的是四个真实缺陷：

| 缺陷 | 现象 | 本质 |
|---|---|---|
| gfx12 WMMA 的 B 操作数打包错误 | 注意力输出只剩 1/8 通道（其余为 0） | 手写 MMA 的 B fragment lane 映射把"输出列"当成了"K 行" |
| LayerNorm 单 lane 全 mask shuffle | 归一化结果非有限值/偏差大 | `__shfl_sync(0xffffffff, x, 0)` 只在 lane 0 调用 = UB |
| 视觉权重 norm 被多加 1.0 | 全 BF16 档跑出全银/全白 | 导出的是最终 gamma，不是 delta |
| merger 输出被乘 0.1 | 单色块位置信号弱到读不出，模型靠文本先验乱答 | 拼接必须原幅，缩放是历史补丁 |

修完的效果：

- 九图定位（纯色、四象限、半图、上下分色、三色条、小红块四角）**三档权重各 9/9**
- 真实照片 16 问（颜色/计数/OCR/物体/地标/朝向/轮子数）**与 llama.cpp 16/16 打平**
- 泛化用例：非正方形图、一图两目标、一请求多图、48×48 小目标，全对
- 开放问答（不是题库）：金毛犬照片 → 认出犬种、朝向镜头、白色瓷砖地面、室内场景；红绿灯照片 → 三灯式结构、最下方红灯亮、绿色外壳、蓝天树木背景

### 3.4 多模态的边界：这是"看图说话"的 VLM，不是生成模型

- **它是理解型多模态**：视觉塔把图片编码成 196 个 token，拼进文本序列，由同一个语言模型回答 —— 能描述、能 OCR、能数数、能判位置，但**不生成图片、不生成视频**。这一点和 llama.cpp 完全一致。
- **和 llama.cpp 的能力等级相同**：两边跑的是同一套 Qwen3.8-27B 权重（我们多一个 BF16 视觉塔覆盖档），`llama-mtmd-cli` 走 mmproj 干的也是"图片 → token → 语言模型"这件事，不存在我们弱一档的情况。
- **没系统验证的是什么**：密集文档 / 表格数值、图表读数、细粒度 bbox 定位、长视频、多图因果推理。这些属于**模型本身的能力边界**，换成 llama.cpp 也一样，不是引擎的短板。

## 5. 工程上踩过、也值得讲的坑

1. **gfx12 WMMA 的 B fragment 映射**：手写 m16n8 模拟时把 B 的 lane 语义弄反，注意力输出只剩 1/8 通道。定位方法：Q=K=0、V 取不同值的恒等测试 —— softmax 后必须原样等于 V，一下就能看出只有 1/8 通道对。
2. **增量编译造成的"假 bug"**：改头文件后只重编一个 TU，结构体偏移在主/客 TU 间不一致，读出的 `next_extents` 是垃圾值，导致 3.2e9 次循环、看起来像死锁。教训：改头文件必须全量重建。
3. **评测语料本身是坏的**：一批 needle 语料的中文问题在生成时变成了 U+FFFD，模型只能看到英文诱饵指令，于是"答非所问"。修语料前，6/8 的失败全是假的。
4. **`--ctx` 给大了会静默降速**：显存池超过可用量时引擎不报错，只切半速路径（350/11.8 vs 423/25.3）。
5. **视觉的"权重被弄坏"是误判**：查到最后是加载器多加 1.0、patch 双帧权重只导了一帧、merger 被缩 0.1 —— 三个都是代码约定问题，不是权重问题。

## 6. 能耗/效率视角（适合视频里讲）

27B 模型每 token 必须把 **11.76 GB 权重**完整读一遍。在 ~500 GB/s 有效带宽的卡上：

```
100% 带宽 → 18.2 ms/step → 54.9 tok/s（理论上限）
当前 28.2 ms/step → 417 GB/s → 35.7 tok/s（约 65%）
```

已经验证到顶的部分：MLP 573 GB/s、GDN 投影 590 GB/s、lm_head 549 GB/s。
剩下的是 **GDN 递推的串行延迟**（48 层 GDN 逐层依赖，每步约 7.7 ms 无法用并行度换）。
所以单流 AR 的现实上限约 **41–46 tok/s**，要更快只能上投机解码（已做，105 tok/s）或批处理（未做）。

这段数据很适合讲"为什么消费级显卡跑大模型，瓶颈不是算力而是显存带宽 + 串行依赖"。

## 9. 限制与诚实边界

- **单流 AR 只有 35.7 tok/s**：不是引擎不行，是权重必须整读一遍；MTP 才能到 105。
- **没有批处理/多并发**：多请求排队，不适合做多人服务。
- **16 GB 是硬约束**：262K 上下文靠主机内存归档，主机内存不足会退化。
- **只在 RX 9070 XT + ROCm 7.2 Windows 验证**：gfx1201 专用内核（WMMA/SIMT 路径）不能直接搬到 CDNA。
- **视觉是理解型多模态（VLM）**：能描述图片、OCR、计数、判位置；不生成图/视频。与 llama.cpp 走 mmproj 属同一类能力、同一套权重（详见 §3.4）。未系统验证的是密集文档/图表/细粒度 bbox 这类模型自身边界。
- **量化损失不可精确量化**：默认 artifact 是 Q4/Q5/Q6 混合，全 BF16 覆盖档能跑但未纳入默认发布路径。

## 10. 一句话总结（视频收尾可用）

> 这不是"把 llama.cpp 编译到 Windows"，而是**为了在一张 16 GB 游戏卡上榨出 27B 模型的 262K 上下文**，
> 自己重写了 KV 记忆、投机解码、视觉通路和一套算子 —— 换来的是比上游快 1.5 倍的 prefill、
> 105 tok/s 的对话速度，以及一套能直接接进应用的 OpenAI 接口。
