# 为什么会有这个项目（写在 v0.1.0 发布前）

> TL;DR (EN): A from-scratch HIP port of the NInfer CUDA inference engine to AMD RDNA4 (gfx1201).
> On one RX 9070 XT 16GB it runs Qwen3.8-27B GSQ IQ3_S at 126K context / 22.9 t/s decode,
> and reaches 41.6 t/s with MTP speculative decoding at 65K — about 1.4x llama.cpp on decode,
> 2x with MTP. Everything below is one person, one GPU, and about a month.

## 起点

一台 13600KF + 32GB 内存 + **一张 16GB 的 RX 9070 XT**。

我想跑 27B 的模型，想开 128K 上下文，想要 100 t/s。这三个数放在一起，在 16GB 的卡上是矛盾的：
27B 的 IQ3_S 权重约 11.7GB，跑起来每出一个 token 就要把这 11.7GB 读一遍，
按 640 GB/s 的带宽上限算，理论天花板只有 54 t/s。100 t/s 只能靠推测解码（一次读权重、出多个 token）。

我把能找到的 AMD 项目都看了一遍：hipfire、hipEngine、Radiance 系的若干分支、vLLM 的各种 RDNA4 构建。
它们都在往对的方向走，但没有一个能在 gfx1201 上把「27B + 长上下文 + 推测解码」这条链跑完整。
最后我选了一条最笨的路：**有一条完整的 CUDA 推理引擎（NInfer），我把整条栈往 HIP 上搬。**

## 一个月零几天

时间比我想的长。中间换过一次模型，推翻过两次自己的结论，写下过三份互相矛盾的验收文档。

真正难的从来不是「让它跑起来」，而是**在它看起来已经跑起来之后，发现它说的全是胡话**。
有几个瞬间我到现在还记得：

- attention 的输出恒等于 0，而且不是 NaN 的那种 0。查到最后是在线 softmax 的归一化写在了两个不同的数值域里，
  `exp` 全部下溢，分母为 0，代码里一个「分母为 0 就输出 0」的保护把它变成了完美的 0。没有任何报错。
- 修完之后输出变成一堆重复的、有周期性的乱码。原因是我把写回时的暂存数组维度写错了，
  8 个维度被压缩进 1 个槽。我当时用了一个笨办法验证：把 216 个 slab 逐个查周期性，**216 个全是 32 周期重复**。
- 同一份 126K 的 prompt，有时候 23.5 t/s，有时候 10.1 t/s，代码一个字节没改。
  我把显存、带宽、频率、热量、splits、图节点全排除了，最后发现是 `--ctx` 多开了 4,743 个 token：
  Windows 的显存驻留预算被越过之后，整个 KV 池会被降级到系统内存，读它走 PCIe，约 30 GB/s。
  **不是玄学，是我自己的命令行参数。**
- 还有一次，同一串 token id 喂给 llama.cpp 它答对了，喂给我们它开始循环复读。
  那就是最纯粹的一句结论：引擎的 prefill 数值是错的，和分词、和模板、和采样都无关。

## 我几次想放弃

不是客套话。写完第一版验收文档的第二天，我跑出完全不同的数字。
那种「昨天还对的东西今天不对了」的感觉，比一个明确的报错难受得多。
有一段时间我甚至开始怀疑方向：是不是这张卡就不该干这件事，是不是应该回去用 llama.cpp + kv mem，少折腾一点。

让我撑下来的是很朴素的两件事：一是每一次怀疑都还能被实验证伪（有几次证伪的是我自己的结论，
比如我一度把 llama.cpp 的速度测低了 40%，那是我机器自己的问题，不是它的问题）；
二是每修掉一个 bug，速度或正确性就真的往前走一格，不是玄学抖动。

## 关于模型：我一度怀疑过国产开源模型

这个项目从头到尾的代码、调试、文档，是 DeepSeek 和 GLM 写的。
中间有几次我被一个 bug 卡到怀疑人生，第一反应是「是不是国产开源模型的能力就到这了，
要不要把闭源模型（Claude、GPT）拉进来试试」。

事实是：**完全不需要。**

最后把这些 bug 挖出来的，不是更强的模型，而是更笨的方法：
把中间张量按字节 dump 下来对拍、把 216 个 slab 逐个查周期、把同一串 token id 喂给两个引擎比输出。
这些方法不需要模型多聪明，需要的是它愿意一次次陪着做枯燥的事、并且不糊弄。
我倒过来想：如果一个模型在明确知道「这次测的基线可能被我自己的机器环境影响」时，
会主动说「这个数字可能是错的，我重测一遍」，这就够了。

## 这个项目是什么，不是什么

它是一个**能用的引擎**，不是论文，也不是万能方案：

- ✅ 正确性：29 token 到 126K token 全部通过（needle 逐字符命中、长文摘要语义正确）
- ✅ decode：同卡同权重下比 llama.cpp 快约 1.4x，开 MTP 后中长上下文约 2 倍
- ❌ prefill 在 64K 以上还落后 llama.cpp 约一半 —— 这是下一个版本要打的
- ❌ 多模态、int8 KV、fp8 KV、dflash2 都还不能用（工程债，见 CHANGELOG）
- ⚠️ 只在一张卡、一个驱动版本、一个 Windows 版本上验证过

它的意义可能是：**在 AMD 的卡上，「CUDA 世界的引擎能力」是可以被搬到 HIP 上的**，
代价是有人得愿意一个 bug 一个 bug 地搬。这件事我之前没在 gfx1201 上看到有人做完过。
