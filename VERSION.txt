本版核心：KV 召回的宽度回归修好（0.1.1 → 0.1.2）
--------------------------------------------------------------------------------

0.1.1 在长上下文召回上引入了一个回归：r9 是「以打分最高的页为中心，取召回预算
（默认 112 页 = 7168 token）那么宽的一整段」；0.1.1 把单段宽度改成 `预算 / divisor`，
divisor 默认还按归档量在 2 和 4 之间自动取 —— 于是 112 页的预算被切成 56 或 28 页的
窄块，围绕多个峰值分散放置。

单文档 needle 语料上这直接把答案文档切掉了（98,218 token、needle 在第 768~800 页）：

  窄块（以峰值页 760 为中心、56 页宽）  召回页 732..787   输出 `45 10052 248046`（错）
  整段（r9 行为）            召回页 704..815   输出与参考逐 token 一致

修复不是改默认参数，而是把「单整段」重新做成两种策略里的默认实现：
  - 单整段（默认）：取 top-1 页，`begin = peak - 预算/2`，`NINFER_KV_RECALL_BACKOFF`
    仍可按 r9 的语义覆盖中心偏移。
  - 多峰（显式 `NINFER_KV_RECALL_DIV>1` 才启用）：把预算切成窄块绕多个峰值，
    再用 `NINFER_KV_RECALL_FILL`（默认开，仅此模式生效）把剩余预算逐页补满。
    `DIV=1` 时整段已用满预算，fill 不再参与。

另外两个配套修正：

  * `build/_gate.py` 的默认 exe 还指向 2026-11-09 的旧二进制（`infer_mini_nordc.exe`），
    导致门禁在过期的可执行文件上测；现在默认 `build/infer_mini.exe`。同一原因也解释了
    「96k 掉一半」的假警报 —— 那是另一件事：KV 池装不下时引擎会静默降速。
  * 96k 门禁臂的 ctx 从 110000 降到 100000：prompt 98,155 token、权重占 11.76 GB 后
    只剩 3.81 GB，110000 的池要 1.97 GB、只留 1.23 GB 启动余量，引擎会**无声地**
    切到半速路径（prefill 350 / decode 11.8，而不是 424 / 24.8），日志里没有任何报错。
    池装得下就是正常速度；这条写进 docs/KVMEM.md，避免下次再当成功耗回归。

召回行为验证（默认参数，无额外环境变量）

  98K needle、常驻窗口 32768：needle 深度 25% / 50% / 75% 三档，召回输出与
  「窗口装得下全文」的完整上下文输出逐 token 一致；92% 那一档 needle 本来就在窗口内，
  两条路径都答语料里那句干扰指令，内容相同（只有空白 token 的切分方式不同）。

服务端场景矩阵（`build/_serve_matrix.py`，一次起进程跑 9 个场景，9/9 通过）

  models / 普通补全 / SSE 流式（28 chunks）/ 单图视觉 / 两图视觉 / 多轮召回 /
  content part 缺 type 的降级 / 坏 payload / 超长 prompt

其中两项是本版修掉的 HTTP 语义缺陷（此前都返回 500）：

  * 请求体形状不对（例如 `"messages": "not-a-list"`）现在返回 400
    `invalid_request_error`，不再是 500；
  * prompt 超出引擎上下文现在返回 400 `invalid_request_error`，并保留原始
    `prepared prompt exceeds Engine max_context N` 文本，不再伪装成 500
    `internal_error`。

0.1.1 的核心工作（历史，仍然有效）：视觉链路修好
--------------------------------------------------------------------------------

0.1.0-pre-r9 的引擎能读图，但空间理解是错的：单色块位置题几乎一律答 top-left，
纯色/半图/上下分色多数错。本版把整条视觉链路查通并修好，九图回归从 3/9 到 9/9。

三个真缺陷（都是引擎 bug，不是模型能力问题）

  1. gfx12 WMMA 的 B 操作数打包错（`ops/common/mma.cuh`）
     硬件 WMMA 的 B 片段按输出列分布（lane L 的列 = L&15、K 半区由 L<16 决定），
     原实现按行分布打包，导致 packed attention 的输出只剩 1/8 通道、其余 7/8 恒为 0。
     定位方式：identity softmax（Q=K=0、段长 1）时输出应等于 V，实测 9216 个元素里
     错 8064 个，正好 7/8；再用孤立 16x16x16 identity GEMM 在软/硬两条 MMA 路径上对拍
     （软路径 0 错、硬路径 120/128 错），把范围锁死到硬件片段映射。
     修复后用同一组探针验证：identity 与随机数据、tile 16/32/64 全部 0/9216 错。

  2. paired D=1152 LayerNorm 的 warp shuffle UB（`ops/kernel/layer_norm.cuh`）
     诊断统计分支在 `if (threadIdx.x == 0)` 里用全 mask 调 `__shfl_sync`，
     单 lane 参与整 warp shuffle 属未定义行为，使专用核输出的 mean/count 变垃圾。
     正式 `test_layer_norm.cpp` 默认路径四个对齐 D=1152 用例全部产出非有限值；
     修掉后默认路径 `OK layer_norm correctness`，真实图片的 norm2 与独立 NumPy
     对拍从 rel 0.067 降到 1.5e-5（903168 个元素仅 29 个非位精确）。

  3. merger 输出被默认 0.1 缩放（`models/qwen3_5/execution/vision.cpp`）
     merger 的训练目标就是把视觉特征投到文本 embedding 的同一空间，拼接必须原幅；
     默认再乘 0.1 后，大面积内容（纯色、半图、上下分色、三色条、四象限）仍读得出来，
     但**单个色块的位置信号被压到读不出来**，模型退化成文本先验 → 一律答 top-left。
     本版默认不缩放；只有显式设置 NINFER_VISION_SCALE 时才按给定因子缩放。

两个权重合同（BF16 覆盖档专用）

  4. patch embedding 是**双帧**权重：mmproj 里 `v.patch_embd.weight` 与
     `v.patch_embd.weight.1` 各一份（t0/t1）。原导出只取 t0 并把同一通道平面复制到
     两个 temporal 槽；正确排列是按通道交错 `[c0t0, c0t1, c1t0, c1t1, c2t0, c2t1]`
     （与 processor 的 `[c][t]` payload 顺序一致），并按引擎 loader 的转置约定落盘。
  5. layer-norm gamma 曾被多加 1.0：导出的是最终 gamma（含负值、均值 0.47~1.31），
     不是 delta；多加 1 会让全 BF16 档塌成银灰（quad4 四块全银）。
     二分法定位：patch+attention、patch+mlp、patch+norm_bias 都正常，
     只有 patch+norm_weight 破坏；修掉后全 BF16 档与默认档一致。

验证（固定 temperature=0.0、seed=42，每例独立进程）

  九图回归（红块/四象限/三色条/左右分色/上下分色，含四个单色块位置题）
    默认档（artifact 量化视觉层）      9/9
    patch-only BF16 覆盖档             9/9
    全 BF16 视觉覆盖档                 9/9
  真实照片交叉验证（Wikimedia 原图 7 张、16 问：颜色/计数/OCR/形状/物体/地标/事件/
  字母数/灯罩数/朝向/轮子数）
    本引擎 16/16 · llama.cpp（BF16 mmproj）16/16 —— 用更差的量化权重打平
  泛化用例（不在九图集内，全部正确）：320/480 非正方形、一图两目标、一请求两图、
  48x48 小目标

本版核心二：OpenAI 兼容服务（新增）
--------------------------------------------------------------------------------

`infer-serve.exe` 是一个自包含的 HTTP 服务，实现 OpenAI Chat Completions 兼容接口：

  POST /v1/chat/completions     支持 stream=true 的 SSE 真流式（首字节约 0.05 s）、
                                content 里混排 {"type":"text"} 与 {"type":"image_url"}
  GET  /v1/models               列出可用模型名
  GET  /health                  存活与视觉是否可用

  图像输入支持 PNG / JPEG / GIF / BMP / TIFF（WIC 解码，无外部依赖；带 alpha 时合成白底），
  自动缩放到模型约定的 448 网格。

  启动（路径按本机调整）：
    set PATH=C:\Program Files\AMD\ROCm\7.2\bin;%PATH%
    infer-serve.exe --model E:\infer-models\Qwen3.8-27B-GSQ-RCO-IQ3_S-ninfer-v3.ninfer ^
                    --ctx 32768 --kv rk4v4-e8 --spec mtp --draft-tokens 2 --port 8099

  源码入口：harness/serve_mini_main.cpp；构建脚本：harness/build_serve.py
  （不依赖 CMake，直接用 ninfer_hip.lib 链接）。

未修 / 已知限制（见 docs/PATCHLIST.md 末节）
--------------------------------------------------------------------------------

  NVFP4 TMA 两个 TU（nvfp4_w4a4_tma.cu / nvfp4_linear_swiglu_w4a4_tma.cu）属 CUDA-only
    的独立 CMake target `ninfer_nvfp4_non_rdc`，ROCm 构建不编；harness/full_rebuild.py
    会无差别扫 .cu，故会报 CUtensorMap/CUresult 未定义，属预期，不影响 ROCm 产物
  serve_mini 未注册进 ninfer/apps/CMakeLists.txt，发布用 harness/build_serve.py 独立构建
  int8 KV 非确定性 · fp8 KV 的 QK 是 __builtin_trap() 桩 · dflash2 坏路径
  126K 以上 MTP（差 0.5 GB 预算）· prefill >=64K 落后 llama
  256K 可用，但必须开窗口 + 主机归档（裸跑装不下）；--ctx 上限 262,144 是模型的
    max_position_embeddings（startup.cpp:752-755 直接拒绝更大值），实测到 260,909
  短上下文 45 t/s 未达（AR 37.3，物理上限 54）
  召回仍需先读完 prompt（query 在 prompt 结束后冻结）；打分是 pre-RoPE 页均值点积，
    再用归档 int4 K 对 top-256 精排兜底（实测精排不移动峰值，只是稳健性保险）；
    默认取以峰值页为中心的整段 112 页，已在 25%/50%/75% needle 深度与 196K/250K/261K
    深度上与完整上下文逐 token 对拍一致
  多文档场景：默认策略是自适应 —— 次峰同时满足「距 top-1 ≥ 28 页」且「得分 ≥ 0.35×top」
    时，把 112 页预算切成两段 56/56（主段前偏、次段居中），否则退化为单整段，与 r9 行为
    逐 token 等价。实测：98K 单针语料次峰仅 1.5% ⇒ 不切分，召回页 704..815 不变、逐 token
    等于 GT；双文档语料次峰 82% ⇒ 切分，问次峰事实能答对（不切分时答成主峰文档的事实）。
    已知限制：两份文档的口令若是近似字符串（NINFER-<NAME>-<NNNN>），两段同时在上下文里时
    模型会把一个名字与另一个的数字拼起来（实测答 NINFER-ATLAS-2222），属模型行为而非投递
    缺陷，判别语料要用不可混淆的事实（一份口令、一份日期）。另：分块不能靠加预算，
    DIV=2 + PAGES=168（84+84）反而把 needle 打坏，总预算必须维持 112 页。

重要用法与安全铁律
--------------------------------------------------------------------------------

  --ctx 必须贴近实际 prompt 长度（126K：ctx126464 → 22.9；ctx131072 → 10.1）
  MTP 只用 --draft-tokens 2；>=100K 真实上下文关 MTP
  引擎 exe 裸双击需要 ROCm DLL 在 PATH：bin/chat.bat 已自动补
  绝不对卡在 GPU 上的引擎进程 Stop-Process（会让 GPU 队列永久卡死 → 黑屏硬复位）
  不要跑 --no-graph + NINFER_PROFILE_* + --spec mtp 组合
  扫测进行中禁止编译/链接（构建会 taskkill 引擎进程并改写 exe）
